Low-level design · main @ 309894a

Eyrie, module by module.

A local portal and control plane for AI coding CLIs: Claude Code, Codex and Gemini CLI, each behind a tool adapter. One FastAPI process on loopback reads the tools' own files, changes things only through their CLIs or a private tmux server, and logs every change. It ships as a tray app with the server and UI bundled, as .deb/.rpm packages, or as a server-only tarball. This page describes what the code on main does. Anything not built is tagged planned.

01 / System context

What talks to what

Everything runs as you, on one machine. The backend is the only thing that touches tool state, and both clients go through its API. The only network call off the machine is the widget's daily release check (and the installer's download).

R = read only. R/W = Eyrie writes there. R (+W) = read, and Eyrie writes only the agent-memory folder. The dashed box is outside the machine. The three CLIs write their own transcripts, DBs and config files; Eyrie only reads them, and changes MCP and plugin config by running the CLIs.

Read path

The source registry (sources/base.py) holds one object per enabled source. Each has available() and snapshot() and reads files on request, with caches keyed on file stat where a read is expensive. Tool-specific reading (transcripts, MCP config, known directories, activity) is delegated to the tool adapters, filtered by tools.enabled on every request.

Write path

Six declared actions build argv lists for claude, codex, gemini or tmux, using the adapters' argv builders. Three file writers edit files directly with etags: tasks, agent memory, and setup (eyrie.toml). There is no generic command endpoint.

Tool adapters (app/tools/)

One frozen Tool per CLI: id, title, binary, home, and optional capabilities sessions, usage, mcp, plugins. An adapter supplies data and argv and never runs anything. ToolId is a Literal built from the registry, so the API models stay in step with it.

Packaged app

The Tauri widget bundles the PyInstaller onedir eyrie-server and the built UI as resources. At launch it makes sure the background service runs its version and opens /setup once if nothing is configured. It checks GitHub releases once a day.

03 / Key flows

Sequences

Solid arrows are calls; dashed arrows are replies. Diagrams scroll sideways on narrow screens.

3.1 Starting a session

The UI generates the session name, and the conversation id when the tool lets Eyrie pick it (picks_conversation_id, Claude new only), before the preview, so the previewed argv is exactly what runs. The dialog offers only enabled, installed tools with sessions, and only their modes. sessions.start isn't destructive, so no confirm; sessions.stop is, and gets a 428 until confirm: true.

3.2 Browser terminal

Browsers can't set headers on a WebSocket, so the token rides as a subprotocol. The pty isn't the tmux client's controlling terminal, so Eyrie sends SIGWINCH itself after each resize.

Close codes: 4000+status (4401, 4403) from the middleware and 4404 / 4503 from the router are sent before accept, so the browser sees a failed handshake (the server answers HTTP 403). 4429 is sent after accept.

3.3 Summary poll: home page and widget

One endpoint answers "what needs me?" for both views, so they can't disagree. Tools you haven't enabled get no health entry and no attention items. summary.tasks is null without a tasks file, and the views hide tasks then.

Attention kindSeverityWhen (summary.py)

3.4 Building the usage index

Tools prune old transcripts (Claude Code does), so usage.db is the system of record, not a cache. Scans run inline on request, throttled to once per 10 s, with no background worker. Which files to read and how a JSON line becomes a row is each adapter's usage capability. The readers are resolved per scan, so a tool enabled later starts being indexed without a restart.

One Claude API response is written as several transcript lines that repeat its usage, so summing lines overcounts. Keying each call and keeping the max of each counter fixes that and makes rereads idempotent. Codex's older rollouts only have token_count events, whose running total repeats when nothing changed, so they're keyed on (session, running total); once a file has token_usage_record lines, its token_count events are ignored. Codex and Gemini count cached tokens inside input, so the adapters store only the uncached part as input. Codex now has per-day usage like Claude.

3.5 External session detection

Sessions you started in your own terminals are listed alongside Eyrie's. Only the tool name and a resume target are taken from each command line, because the arguments can hold a prompt.

3.6 Editing tasks or agent memory with etags

Obsidian and the agents edit the same files, so every write carries the etag the client read. The etag is a content hash, so mtime granularity can't fool it.

Tasks (sources/tasks.py)

  • File: paths.tasks, an absolute .md path set at first run or in Settings. No default: the Tasks page, home card and widget "+ Task" stay off until it's set.
  • Created with a header on first add; its folder must exist (else 409).
  • Task id: sha1(text)[:10], plus -n for duplicates. The checkbox isn't hashed, so toggling keeps the id.
  • Only the target line changes. New tasks go after the last task. CRLF is preserved. Unknown id: 404 with current.

Agent memory (sources/memory.py)

  • Files: ~/.claude/agent-memory/<agent>/*.md (Claude Code subagent memory; paths.agent_memory overrides; the folder itself may be a symlink); no new agent folders.
  • Shown only when Claude Code is enabled and the folder exists (features.agent_memory).
  • Create uses If-Match: absent. 1 MB per file. Read returns linked_from.
  • Delete moves to ~/.eyrie/trash/agent-memory/<agent>/, timestamped on a name clash.

3.7 First-run setup and Settings

The UI loads /meta at startup. While configured is false (no config file at $EYRIE_CONFIG or ~/.eyrie/eyrie.toml, and no <repo>/eyrie.toml), every route redirects to /setup. /settings is the same page against the same endpoints, later.

Setup owns three keys: tools.enabled, sessions.roots and paths.tasks. The write parses the existing TOML, sets those keys and regenerates the file, so other tables ([pricing], [privacy], …) survive but comments don't. EYRIE_* env vars still win at the next start. Obsidian vaults are offered only as a starting folder for the tasks file, never as a default.

3.8 Release to install

One tag builds every artifact, tests the installers, and publishes them. Every install path ends in eyrie-server service install --ui-dir …, which is idempotent and rewrites and restarts the service. install.sh and the app run it themselves; the Homebrew formula's caveats tell you to run it, and the cask's tell you to launch the app once. An upgrade repoints the service at the new binary, and running sessions survive (AbandonProcessGroup, KillMode=process).

Linux packages put the app at /usr/lib/Eyrie (eyrie-server/eyrie-server, ui/). The script copies the macOS app to ~/Applications/Eyrie.app, and --user unpacks to ~/.local/lib/eyrie/<V>, links current to it and adds ~/.local/bin/eyrie-server. A browser-downloaded .dmg is dragged to Applications and needs right-click → Open once, because builds are unsigned. Homebrew: render.py <version> <tap> writes the formula and cask, which you commit to abrahamalen/homebrew-eyrie yourself; the release job doesn't touch the tap.

07 / Deployment

One process, one port, per user

Native, no Docker: a container can't drive the host's tmux or the host's CLIs with your credentials. Every mode runs the same eyrie-server serve (or uvicorn --reload in dev).

macOS: launchd agent local.eyrie

  • ~/Library/LaunchAgents/local.eyrie.plist via plistlib, checked with plutil -lint.
  • RunAtLoad, KeepAlive, ThrottleInterval 10.
  • AbandonProcessGroup: restarting Eyrie never kills its tmux sessions.
  • launchctl bootout (waits until it's gone) then bootstrap gui/<uid>.

Linux: systemd user unit eyrie.service

  • ~/.config/systemd/user/eyrie.service, systemd-quoted args.
  • Restart=on-failure, RestartSec=5.
  • KillMode=process: only Eyrie stops, tmux sessions keep running.
  • daemon-reload, enable, restart. Tip: loginctl enable-linger.

PATH capture

launchd and systemd user units start with a minimal PATH, so the CLIs and tmux wouldn't be found. At install, login_path() runs $SHELL -lic 'printf "__EYRIE_PATH__%s__END__" "$PATH"' with only HOME USER LOGNAME SHELL and TERM set. It takes the value between the markers (so shell noise doesn't matter) and writes it into the plist or unit. It falls back to the current PATH. Install notes a missing tmux and lists which tool CLIs it found; first-run setup decides which tools are used. Re-run service install (or make install) after an upgrade.

Packaging

Server binary

PyInstaller 6.22.3 onedir (make server-dist), because onefile took 6–10 s to start on macOS. Tauri's externalBin takes a single file, so the folder ships as a resource at <resources>/eyrie-server/eyrie-server, next to <resources>/ui. websockets is pinned in requirements.txt, because without it the terminal handshake fails at runtime.

Versions

VERSION is the single source. make version V=x.y.z writes the 7 copies, and make version-check fails make check if any differ. The release job refuses a tag that isn't v$(cat VERSION). Tags with - publish as pre-releases.

Updates and signing

No auto-update. The widget GETs api.github.com/repos/abrahamalen/eyrie/releases/latest at most once a day (checked hourly, timestamp kept in its settings). It compares the first three numeric parts, and a newer tag adds an "Update available" menu item that opens the release page. Builds are unsigned for v0.2; Linux packages are verified by SHA256SUMS only.

08 / Known limits and next steps

Where it's thin

Limits in today's code

  • Gemini is validated only against upstream formats. tools/gemini.py follows gemini-cli's source (storage, project registry, chat recording), and the tests use fixtures built from that, not from a real install. Older single-file .json sessions are skipped.
  • Not everything is per tool yet. MCP failures come only from Claude transcripts. /sessions/conversations (the Sessions page's resume list) is Claude only. Plugins and agent memory are Claude only. There's no Gemini source page. The MCP source's available() still checks ~/.claude.json.
  • Masking is by shape. A secret with none of the known shapes (say, a bare random string as a positional arg) still shows.
  • Polling, not push. Every view polls (Sessions every 4 s, summary every 10 s from each client), and each summary runs ps plus tmux calls.
  • Release pipeline coverage. Only x86_64 Linux packages are install-tested; arm64 .deb/.rpm are built but not installed in CI. The Homebrew tap is updated by hand.
  • GET /sessions/{name}/screen is served but no page calls it any more; the terminal replaced the screen preview.
  • Cost reads slightly low: Claude Code doesn't log some background calls (titles, compaction). The Usage page says so.
  • The terminal limit (8) is a per-process counter, which is fine for the single uvicorn worker Eyrie runs.

Built and next

Tool adapters built

app/tools/: Claude Code, Codex and Gemini CLI behind sessions, usage, mcp and plugins capabilities. ToolId comes from the registry. Codex has per-call usage, through usage.db schema 2. The UI is built from /meta.

Gemini CLI built

Sessions, external detection, usage and MCP. It's validated against upstream formats only, so check it against a real install. Gemini extensions and an Antigravity CLI adapter are open questions.

First-run setup and Settings built

app/setup.py + routers/setup.py: detect, suggest roots, offer vaults, write ~/.eyrie/eyrie.toml (merged, etag-checked, audited) and apply live. /setup until configured; /settings later.

Packaging and releases built

Onedir eyrie-server bundled in the Tauri app (dmg, deb, rpm), server tarballs, release.yml, install.sh, Homebrew generator, daily update check. Tested locally and against rc tags.

Auto-update planned

Tauri's updater plugin with a signed manifest on GitHub Releases, once releases are regular. Today it only notifies.

Signing, apt/dnf repos planned

Developer ID signing and notarization once browser downloads are the main install path. Hosted, signed apt and dnf repositories.

Windows deferred

Needs a session layer without tmux, a ConPTY terminal bridge and a per-user scheduled task. install.sh refuses non-Darwin/Linux.

Subagents per session idea

List a session's Claude subagents from ~/.claude/projects/<proj>/<session>/subagents/agent-*.jsonl plus each .meta.json (description, agentType, finished). The usage index already reads those transcripts for cost.
